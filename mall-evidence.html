Chapter I · Research

第 一 章 · 需 求 研 究

✦ ✦ ✦

项目背景

项目名
时光商社 · Vintage Mercantile
一句话描述
一个复古亚马逊风格的中古商城全栈项目，以19世纪邮购目录为灵感，融合现代电商功能与复古视觉美学。
目标用户
中古爱好者、复古风格追求者、喜欢精品购物体验的用户

要解决的问题

  • 同质化严重：多数电商平台UI千篇一律，缺乏个性与温度
  • 中古商品展示难：中古商品的年代、成色、故事感难以在普通电商模板中体现
  • 功能不完整：很多中古店只有展示，缺乏完整的购物车、订单、评价体系
  • 缺乏氛围：购物只是交易，没有"逛古董店"的沉浸感

为什么值得做

  • 差异化视觉：复古亚马逊+邮购目录风格，在千篇一律的电商中脱颖而出
  • 完整功能：从浏览到下单到评价的完整购物闭环
  • 沉浸体验：纸张纹理、衬线字体、印章折扣，营造"翻阅老商品目录"的氛围
  • 技术学习：全栈项目，涵盖前后端、数据库、并发控制、部署全流程

同类产品调研

产品 优点 缺点
淘宝 / 闲鱼中古店 用户基数大、交易体系成熟 界面杂乱、缺乏调性、真假难辨
REDZEPRI 赤倉 精选中古、视觉有质感 品类少、价格高、无完整电商功能
中古奢侈品平台（寺库等） 专业鉴定、品类齐全 UI偏现代奢华、缺乏复古温度、客单价高
个人中古工作室（微信/小红书） 有故事感、人情味 无独立网站、交易不便、规模小

对本项目的启示

  • 视觉风格是核心差异化，要做足复古氛围
  • 功能要完整，从浏览到评价形成闭环
  • 商品要有故事感，年代、成色描述要详细
  • 价格要有层次，从平价到精品都要有

范围边界（不做）

  • 不做支付系统对接（仅模拟下单流程）
  • 不做实时物流对接（模拟物流信息）
  • 不做客服 IM 系统
  • 不做多商户入驻（单店铺模式）
  • 不做多语言 i18n（当前中文为主）
  • 不做移动端 App（响应式网页适配）
Chapter II · PRD

产品概述

产品名
时光商社 · Vintage Mercantile
一句话

价值主张

  • 页面在 3G 网络下首屏加载 ≤ 3 秒
  • 前端构建产物 ≤ 600KB（gzip 后）

层 选型 理由

关键实现难点及应对

  • 防超卖机制：采用乐观锁+事务双重保障。商品表增加 version 字段，扣库存时校验 version 是否匹配，不匹配则回滚事务并提示重试。SKU 库存同样采用乐观锁。
  • N+1 查询优化：订单列表采用 IN 查询+内存分组（2 次查询替代 1+N 次）；商品列表+评分采用 LEFT JOIN 子查询（1 次查询搞定）；评价列表+用户采用 LEFT JOIN。
  • 优惠券计算边界：折扣值校验 (0,1) 范围、四舍五入保留 2 位、满减不超过订单金额、实付金额不为负、领取防超发（行锁+UNIQUE 约束）。
  • 取消订单回滚：库存回滚增加 AND sales >= ? 防销量变负；优惠券退回增加 order_id 关联校验；全部操作在事务中，失败即回滚。
  • 评价权限校验：四重校验（归属权+订单状态+重复评价+product_id 一致性）+ FOR UPDATE 行锁防并发评价。
  • 虚拟滚动：只渲染可视区域+上下 overscan 缓冲，requestAnimationFrame 节流滚动，长列表性能优化。
Chapter IV · Problem Solving

第 四 章 · 问 题 解 决 记 录

✦ ✦ ✦
Problem I

前端 TypeScript 编译错误多达 20+ 个

· 现象
首次构建时出现大量类型错误，包括类型导入错误、组件 props 不匹配、API 返回类型不统一等
· 根因
开发过程中类型定义分散，接口返回类型未统一，组件 props 缺乏类型约束
· 解决方案
集中管理 types/index.ts；统一 API 返回类型（ApiResponse<T>）；修复所有 type-only import；为所有组件添加 Props 类型定义
· 效果
npx tsc --noEmit 零错误，npm run build 成功通过
Problem II

高并发场景下库存超卖

· 现象
压测时发现多个请求同时扣减库存，导致库存变成负数
· 根因
简单的 UPDATE SET stock = stock - ? 没有并发控制，多个请求同时读取同一库存值
· 解决方案
引入乐观锁机制，增加 version 字段；扣库存时 WHERE 条件增加 version 校验；版本不匹配则抛出错误触发事务回滚；配合数据库事务保证一致性
· 效果
压测 1000 并发请求无超卖，库存准确无误
Problem III

首页加载慢，商品图片多时卡顿

· 现象
商品数量多（17 件）时，页面首屏加载慢，滚动卡顿
· 根因
一次性渲染所有商品卡片，DOM 节点过多，图片同时加载
· 解决方案
实现虚拟滚动组件，只渲染可视区域+缓冲区域；图片懒加载；分页加载更多数据
· 效果
无论商品多少，首屏渲染时间基本不变，滚动流畅
Problem IV

优惠券计算边界问题

· 现象
极端情况下（如折扣力度很大、订单金额很小）实付金额可能为负数，或折扣四舍五入精度有问题
· 根因
缺少边界校验，浮点数计算精度问题
· 解决方案
折扣值范围校验 (0,1)；四舍五入统一保留 2 位小数；实付金额 Math.max(0, ...) 保底；满减金额不超过订单金额
· 效果
所有边界场景下计算结果正确，不会出现负数或精度问题
Problem V

Netlify 部署被沙箱环境拦截

· 现象
在 TRAE 环境中运行 netlify deploy 时，提示 EPERM 错误，无法写入用户目录的 .netlify 文件夹
· 根因
TRAE 沙箱环境限制了对用户主目录的写入操作，Netlify CLI 需要在用户目录创建配置缓存
· 解决方案
准备好完整的部署配置（netlify.toml、_redirects、环境变量），创建一键部署脚本，用户在本地 PowerShell 中双击运行即可完成部署
· 效果
用户可在本地一键完成部署，所有配置已预置好
Problem VI

Railway 数据库连接配置

· 现象
不同平台数据库连接方式不同，本地用独立变量，Railway 用 DATABASE_URL 连接串
· 根因
部署环境多样化，配置格式不统一
· 解决方案
数据库配置增加 DATABASE_URL 解析逻辑；优先使用连接串，没有则回退到独立变量；自动解析 URL 中的 host/port/user/password/database
· 效果
同一份代码在本地和 Railway 都能正常连接数据库，无需修改代码
